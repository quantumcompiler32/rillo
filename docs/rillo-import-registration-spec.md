# Rillo: reviewed screenshot import, section planning, and registration calendar

## Problem Statement

A Milpitas Middle College student planning courses across community colleges must manually transcribe multi-term plans, distinguish intentions from actual enrollment, compare section choices, track authorization paperwork, and assemble dates and locations from separate sources. Future sections may not be published yet. A submitted form, a chosen section, and enrollment are different facts, but the current planner cannot represent their relationships precisely enough.

Rillo currently offers browser-local class entry, one simple meeting pattern per class, college-and-term registration plans, dates, JSON backup, calendar export, and limited degree/transfer views. It has no screenshot extraction, review/reconciliation workflow, independent section alternatives, date-bounded conflict checking, or identified automated test suite. Loading and backup import validate only parts of the data structure. These observations are from source inspection, not a completed hands-on acceptance run.

## Solution

Let the student import clear portal screenshots, review and correct extracted entries locally, save only student-confirmed records, and see a plan organized by term. A planned class can exist before sections are published. When offerings become available, the student manually adds and compares section options, marks preferred and backup choices, and independently tracks form progress, enrollment readiness, and registration status.

Provide a calendar showing enrolled meetings with their times and locations, an optional planning view for alternatives, and distinct tasks/deadlines. Identify conflicts and missing information without claiming eligibility or silently changing records. Keep images on-device and discard Rillo's copies after review ends. Start with Moksh's real workflow, validate on phone and laptop, then pilot with a small MMCHS group.

## User Stories

1. As a student, I want to select several clear portal screenshots, so that I can import a multi-term plan without entering each course manually.
2. As a student, I want to confirm one source college for each batch, so that courses are associated with the correct institution.
3. As a student, I want multiple terms in a batch, so that I can review my longer-term plan together.
4. As a student, I want overlapping screenshots reconciled, so that repeated rows do not become accidental duplicates.
5. As a student, I want images processed on my device, so that my course screenshots are not sent to an external processor.
6. As a student, I want clear format and browser limitations, so that I know when manual entry is necessary.
7. As a student, I want extracted entries alongside their source image on a laptop, so that I can check the transcription.
8. As a phone user, I want to switch between the image and editable review, so that I can correct entries on a small screen.
9. As a student, I want uncertain or unreadable fields highlighted, so that I know what needs attention.
10. As a student, I want to manually correct fields and add or omit entries, so that extraction errors do not dictate my plan.
11. As a student, I want to confirm college, term, course code, and course status before saving, so that required facts are not guessed.
12. As a student, I want missing optional information explicitly acknowledged, so that an omission is distinguishable from a reviewed value.
13. As a student, I want a future planned class to have no section or professor yet, so that unpublished offerings do not block planning.
14. As a student, I want to save ready entries while incomplete entries remain in the active review, so that one unresolved entry does not block the batch.
15. As a student, I want an editable table with a batch confirmation, so that I can save reviewed entries efficiently.
16. As a student, I want proposed additions and differences against existing records, so that reimporting does not silently replace my corrections.
17. As a student, I want to choose which proposed changes to accept, so that I control reconciliation.
18. As a student, I want saved records marked student-confirmed with a brief source note, so that my review is not confused with college verification.
19. As a student, I want planned and enrolled entries kept distinct, so that a course plan never implies completion or earned credit.
20. As a student, I want candidates already extracted preserved during a recoverable failure, so that I can finish the active review manually.
21. As a student, I want cancellation to discard unsaved work and warn about edits, so that my existing saved plan stays intact.
22. As a student, I want Rillo's image copies discarded when review ends, so that original screenshots are not retained with my plan.
23. As a student, I want my saved plan grouped by term and status, so that I can understand my future and current courses.
24. As a student, I want missing information and next actions shown together, so that I can identify what needs attention.
25. As a student, I want several section options attached to a planned class, so that I can compare alternatives without creating several supposed enrollments.
26. As a student, I want to record the college's section and registration identifiers exactly, so that I can find the intended offering when registering.
27. As a student, I want professor, meeting time, location, conflicts, and readiness compared, so that I can choose an option using the information I have.
28. As a student, I want preferred and backup choices separate from registration status, so that a preferred section can also be waitlisted or registered.
29. As a student, I want form preparation, submission, correction, and reported approval tracked, so that I know where my paperwork stands.
30. As a student, I want each submission's course/term or section scope recorded, so that I can see what I actually submitted.
31. As a student, I want enrollment readiness tracked separately, so that submitted paperwork never automatically means cleared to enroll.
32. As a student, I want considering, waitlisted, registered, and in-progress states distinguished, so that my calendar reflects what I have recorded.
33. As a student, I want to retain historical completed and withdrawn course records, so that the new planning model does not erase my existing history.
34. As a student, I want changing my preferred section to preserve submission history and flag coverage for review, so that a different professor or time does not silently inherit clearance.
35. As a student, I want registered and in-progress sections shown by default, so that alternatives do not look like enrolled classes.
36. As a student, I want a planning view of preferred and backup options, so that I can inspect possible schedules before registration.
37. As a student, I want separate lecture and lab meeting patterns, so that every required meeting can appear at its actual time and place.
38. As a student, I want meetings limited to their applicable date ranges, so that different sessions are not treated as simultaneous throughout a term.
39. As a student, I want asynchronous and unknown-time sections listed without invented times, so that incomplete schedules stay visible.
40. As a student, I want form targets, assigned registration appointments, and deadlines distinguished from meetings, so that I can plan both attendance and preparation.
41. As a student, I want tasks linked to college, term, and relevant courses or sections, so that dates have an understandable purpose.
42. As a student, I want conflict warnings that allow saving alternatives, so that I can compare options before choosing.
43. As a student, I want incomplete conflict checks explicitly identified, so that missing dates or times do not look like a conflict-free result.
44. As a student, I want passing a date to leave my reported statuses unchanged, so that the calendar never invents approval or enrollment.
45. As a student, I want my plan to survive save, reload, migration, and backup/restore, so that I do not lose course records or planning relationships.
46. As a student, I want invalid backups and failed writes to preserve my saved plan, so that an error does not replace valid data.
47. As a keyboard or screen-reader user, I want accessible review, comparisons, dialogs, and calendar alternatives, so that I can complete the same workflow.
48. As a student, I want current degree and transfer goals preserved with their limitations, so that this release does not remove the wider planning context.

## Implementation Decisions

- **Delivery model:** extend the existing browser-local application. Do not introduce accounts, sync, a backend, or external image processing. Existing degree/transfer views and supported manual workflows must continue to work. Preserve the simple local-use path; document any additional serving requirement needed by local OCR without introducing a hosted dependency for student records.
- **Logical responsibilities:** separate review/reconciliation and confirmed-plan persistence from extraction, section comparison, and calendar presentation. Prefer a small cohesive plan-workflow boundary to many independently mocked helpers. These are responsibilities, not a mandate for a particular framework or file layout.
- **Domain relationships:** a course belongs to a college; a planned class concerns that course in a term; zero or more section options can belong to that plan. A section has exact college identifiers, instructor information, and zero or more meeting patterns. Preserve distinct enrollment attempts and completed history; do not merge different colleges, terms, sections, or attempts merely because codes or titles resemble one another.
- **Independent state dimensions:** section preference, form progress, enrollment readiness, and registration status remain independent. Form states include not started/preparing, waiting for signatures where already recorded, submitted, correction needed, and approval reported. Readiness includes not checked, clearance needed, and student-reported cleared. Registration retains considering/planned, waitlisted, registered, in progress, completed history, withdrawn, and no longer considering semantics. Existing statuses must migrate without being reinterpreted as official proof. Exact presentation labels can be refined without collapsing these distinctions.
- **Image input and extraction:** clear portal screenshots are the initial extraction scope. Support multiple images for one college and multiple terms. Decode and extract locally through one replaceable extraction adapter that returns candidates with field-level uncertainty and source-image references; extraction cannot save plan records. Preserve visible course/section identifiers, units, statuses, and warnings when readable. Do not fabricate hidden fields, certainty scores, eligibility, or prerequisite results. Preserve unfamiliar warnings as reviewable source text.
- **Feasibility gate:** select a locally executable OCR approach only after testing representative images on phone and laptop. Package or cache necessary resources without transmitting images or extracted student information. Unsupported formats, decoding failure, or resource limitations receive an actionable manual-entry fallback. JPEG/PNG screenshots are the baseline to validate; HEIC is not a release promise without device evidence. Failure of local OCR is not permission to add cloud processing.
- **Review contract:** show an editable table and source view, with responsive image/review switching on phone. Require explicit review of extracted values and acknowledgment of optional omissions before batch confirmation. Core college, term, course code, and status must have confirmed values; unknown core values cannot be saved. An extracted status is a candidate, not an automatic default. Future sections/instructors can be marked not selected yet. Title and units are not required core fields.
- **Partial commit and reconciliation:** let the student commit selected ready candidates while leaving unresolved candidates in the active review. Identify possible duplicates within the batch and against saved records using college, term, course, section/registration identifiers, and attempt information where present. Propose additions, unchanged matches, and field differences; require explicit reconciliation choices. An unknown imported value must not erase a confirmed value. Preserve identity for unchanged records; make repeated accepted imports stable rather than duplicating them.
- **Persistence and recovery:** introduce an explicitly versioned plan schema with stable references for courses/plans, section options, authorizations, meeting patterns, and tasks. Validate records, enums, dates, identifier types, and references before migration, replacement, or commit. Preserve existing classes, registration records, deadlines, degree goals, transfer goals, notes, and identifiers. Migrate supported legacy data conservatively; retain unknown legacy scope as unknown rather than inventing associations. Failed validation or storage writes leave the previous valid stored and displayed plan intact and show a recoverable error. Backup/restore includes all new relationships and acknowledgments; never includes source images or unfinished reviews.
- **Privacy and review lifecycle:** keep image copies and full extraction artifacts transient for the active review. Save only reviewed structured fields, acknowledged omissions, and a minimal source/confirmation note. Do not persist images, full OCR text, unnecessary identifiers, or image contents in logs, backups, telemetry, or caches. Release image URLs and working copies when review completes or is cancelled; this does not delete the student's original files. Saving a subset does not end the remaining active review; discard its image copies when that review ends. Warn about edited unsaved candidates on cancellation. Successfully committed entries remain saved if the student later cancels the remainder.
- **Form scope and readiness:** record actual college, term, form name, submission dates, covered courses and any explicitly covered sections, and reported status. Show exactly what the student recorded rather than assuming form scope from a selected section. SJCC's linked public R-40 supports course-and-term authorization tracking; it does not establish automatic eligibility for all alternative sections. Mission's exact scope remains unknown until supported by its actual instructions/form. Course authorization, prerequisite clearance, assigned registration appointment, and enrollment remain separate. Changing a section preserves historical submissions, leaves new readiness unconfirmed, and flags authorization coverage for review; no automatic copying of enrollment or clearance.
- **Comparison and next actions:** compare recorded instructors, identifiers, meetings, locations, conflicts, and readiness, with visible missing information. The student chooses preferred/backup options; no automatic overall ranking or verified professor ratings. After save, present term-grouped records plus contextual next steps such as recording an appointment, checking coverage, or resolving missing information. Keep personal target dates, college-wide published dates, and assigned appointments distinguishable; include source/applicability and checked-date context for published guidance rather than silently treating existing hardcoded times as personal facts.
- **Calendar contract:** default to registered/in-progress sections. Provide a separately labeled planning overlay for preferred/backup options and filters distinguishing meetings from tasks/deadlines. Each recurring meeting pattern carries days, start/end times, date range, and location or online format. Show times in the applicable college/location timezone, visibly identified when needed; avoid device-timezone shifts that change campus wall-clock times. Display lecture/lab separately. Unknown-time or asynchronous sections remain accessible in an unscheduled list. Missing dates must be identified; do not invent actual dated occurrences. A weekly preview may show known day/time patterns with an explicit incomplete-date label. Calendar time passing never updates reported states.
- **Conflicts:** warn without blocking saves. A confirmed time conflict requires actual overlapping date-bounded meeting occurrences, with overlapping times; touching end/start times alone do not overlap. Handle different term/session ranges and timezones. Report comparisons with missing dates/times as incomplete. Distinguish alternative-versus-alternative overlap from conflicts involving enrolled sections. Do not add travel-time judgments.
- **Existing exports/reminders:** preserve existing JSON backup and calendar deadline-export behavior and verify regressions. The on-screen meeting calendar is in scope; adding full recurring-class export is not a requirement established by this interview. Existing browser alerts remain open-page alerts and calendar export remains the closed-app reminder path, subject to real-device verification.
- **Accessibility:** support keyboard operation, meaningful labels, error association, predictable focus after dialogs and failed confirmation, non-color status distinctions, an accessible list equivalent for calendar content, responsive phone/laptop layouts, and reduced-motion preferences. Do not place implementation details in student-facing flows.

## Testing Decisions

- **Agreed test boundary:** the student-facing browser workflow is the primary and highest boundary: choose images, review, correct, reconcile, save, reload, compare, and inspect the calendar, then export/restore. Moksh explicitly confirmed this approach during specification synthesis. Test external behavior and persistence guarantees rather than rendering helper structure, internal function calls, private storage layout, or implementation-mirroring units.
- **Minimal new seam:** the local extraction adapter is the single substitution point for deterministic browser tests. Supply representative candidates, unknown fields, conflicting entries, and partial failures there; exercise the real review, validation, reconciliation, commit, rendering, and persistence paths. Mocked OCR passing is not evidence that real extraction works.
- **Prior art:** no automated suite, test configuration, package manifest, or existing test harness was identified in this source inspection. The existing browser UI, save/load workflow, JSON backup interface, and calendar export are usable public boundaries. Add only the minimal browser test infrastructure required; do not invent an existing test precedent.
- **Coverage by responsibility:** exercise candidate review and reconciliation, confirmed-plan migration/storage/restore, section comparison/state independence, form scope, and calendar/conflict projection through the primary browser boundary. Use real-image device checks for the extraction adapter. Add lower-level tests only if a critical date/schema rule cannot be reliably covered at that boundary.
- **Acceptance scenarios:**
  1. A multi-term screenshot batch saves every selected reviewed course in its confirmed college and term; enrolled and planned statuses stay distinct and no credit is inferred.
  2. An unreadable required field or missing status blocks only that candidate until explicitly supplied and confirmed; optional omissions need acknowledgment. A future planned class needs no invented professor or section.
  3. Saving ready rows leaves unresolved candidates in active review; cancelling the remainder keeps committed rows and leaves all unrelated saved records intact.
  4. Overlapping images and repeated imports propose reconciliation; accepting unchanged data does not add duplicates. A changed time/status does not overwrite prior data until accepted; unrelated terms/colleges/sections remain distinct.
  5. A cancelled/failed extraction or rejected import does not alter the existing plan. A partial extraction failure retains obtained candidates for manual completion.
  6. Invalid records, broken references, unsupported backup versions, corrupt stored data, and simulated storage failures produce actionable errors without destroying the previous valid plan or falsely reporting a successful save.
  7. Legacy migrations and new-schema backup/restore preserve classes, statuses, dates, notes, source acknowledgments, alternative sections, independent state dimensions, meetings, tasks, degree goals, and transfer goals; repeated reloads do not duplicate them.
  8. Several section options compare correctly; changing preference does not set approval or enrollment. A preferred waitlisted option retains both facts. Unknown identifiers/readiness stay unknown.
  9. A course-scoped R-40 record remains course-scoped when a section changes; a section-specific record is not broadened. New readiness requires review, prior submission history is preserved, and no option inherits registration automatically.
  10. Default calendar meetings include registered/in-progress sections; planning overlays show preferred/backup alternatives distinctly. Lecture/lab times, locations, date bounds, and online format are preserved; asynchronous/unknown schedules remain accessible.
  11. Confirm overlapping meeting occurrences, no overlap for disjoint sessions or adjacent end/start times, and incomplete results for missing times/dates. Conflict warnings allow saving. Planning alternatives do not masquerade as simultaneous enrollments.
  12. Date/time display respects campus wall-clock meaning across a differently configured device timezone and a daylight-saving transition; tasks/deadlines are distinct from class occurrences.
  13. Form targets, personal registration appointments, and sourced general dates retain their meaning. Advancing the clock changes upcoming/overdue presentation without changing form, readiness, preference, or registration state.
  14. Existing deadline calendar export retains event meaning, timestamps, and reminder information in a real calendar app. Existing browser-alert limitations remain clear.
  15. Keyboard and screen-reader users can complete review/correction/confirmation, interpret errors and missing values, compare options, and use calendar/list filters; narrow screens and reduced-motion settings remain usable.
  16. Verify with browser network inspection that real extraction sends no images or extracted student information externally; after completion/cancellation, reload and exported backups contain no original images, full OCR artifacts, or unfinished review data.
- **Real-image/device gate:** assess actual multi-term portal screenshots on a phone and laptop, including overlapping rows, low-quality text, unsupported formats, and local-extraction failure. Report device/browser versions, supported formats, results, and limitations. Never use private student images as public repository fixtures; use consented/redacted or synthetic examples for automated tests.
- **Usefulness gate:** on the same real plan, measure manual entry time against image import plus correction; release acceptance requires the latter to be faster while all saved core fields/statuses match the student's confirmation. Verify duplicate reconciliation and backup/restore. If extraction does not meet this gate, report the limitation and retain manual entry; do not declare the image workflow complete or quietly change the processing boundary.
- **Release evidence:** distinguish automated acceptance results, real-device extraction/privacy checks, calendar-app validation, and observed usefulness. A later small MMCHS pilot follows validation of Moksh's workflow. No tests or acceptance runs are claimed by this specification.

## Out of Scope

- Printed-paper photo extraction in this initial screenshot release, handwriting recognition, and universal image/layout support.
- External image processing, image retention after review, sync/accounts, and saved unfinished review sessions across reloads.
- Live catalog/section discovery, seat availability, automated prerequisite or enrollment-eligibility decisions, form submission, college-account access, or automated registration.
- Automatic professor/section ranking, stored verified professor ratings, and travel-time estimates.
- Full recurring-class calendar export, new background push delivery, and changes to closed-app notification infrastructure.
- Expanded degree audits, new source-backed degree paths, ASSIST retrieval, transfer comparisons, admissions predictions, or official credit/degree determinations. Preserve existing goals and limitations.
- Broad deployment to schools before validating the personal workflow and small pilot.

## Further Notes

- This is a multi-session release specification, not a request to implement every component in one change. Derive self-contained, blocker-ordered implementation tickets next. Save/migration/restore safety precedes committing new import records. Validate local extraction feasibility early enough to avoid promising unsupported behavior.
- The agreed release intentionally includes manual section comparison and registration tracking alongside screenshot import. Future discovery, degree intelligence, and transfer work remain in the product vision.
- Part of the broader [Rillo decision map (#1)](https://github.com/quantumcompiler32/rillo/issues/1). [Evidence states (#2)](https://github.com/quantumcompiler32/rillo/issues/2) is related, but this spec does not close that broader issue or the deferred degree/transfer/reminder questions.
- The public SJCC form linked during planning is marked Rev. 03/2020. It lists approved courses with term/year, without section/CRN fields established by the reviewed extraction. Keep course authorization distinct from section readiness; recheck applicability before shipping college-specific assertions. Sources: [SJCC R-40 PDF](https://sjcc.edu/_resources/PDF/admisssion_and_records/R40.3.30.20.pdf), [SJCC concurrent enrollment instructions](https://sjcc.edu/milpitas-extension/milpitas-concurrent-enrollment.aspx).
- [Mission dual-enrollment guidance](https://missioncollege.edu/office-of-instruction/educational-partnerships/dual-enrollment.html) distinguishes form processing and registration, but readable public form fields did not establish exact authorization scope. Support explicit unknown scope and student-entered records; do not guess. Use each college's actual form/identifier labels.
- Requirement, policy, source freshness, browser support, and extraction quality are validation work, not grounds for changing agreed safety/uncertainty semantics. Rillo remains a student planning tool; a student-confirmed record is not official verification, and a planned course never awards credit.
